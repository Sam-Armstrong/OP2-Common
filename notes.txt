
What to do:

Can LLVM Flang be used to parse OP2 Fortran source code and extract loop
and kernel information with equivalent correctness to the existing translator,
and with measurably better performance?

Existing solution:


Proposed solution:

STAGE 1
Parse the input source and extract the information we need from the Flang AST.
Specifically need two things as output:
  - The argument information for each op_par_loop
  - The source code for each of the kernels, including all functions/subroutines that are called

For 1 this should be fairly straightforward - there's some details to be careful of but more or
less this should just be walking the Flang AST and pulling out the relevant information.

2 requires resolving the reference to the kernel subroutine, then recursively finding the tree of
dependencies. I don't think (?) Flang has a serializable AST or the ability to re-output the AST
to source so for this we'll need to use the source line/character information to extract excerpts
from the original source code.

STAGE 2
Here we'd use the loop metadata and the extracted kernels to validate that the kernels only
perform operations permitted by the specified argument access types and other restrictions.
This is reasonably involved as it requires tracking arguments through child subroutine calls
to check read/write/increment validity - currently we have some scaffolding to allow us to
inspect every time an argument is accessed, we'd need to implement the same for this.

STAGE 3
We've moved to translating Fortran kernel subroutines into C++ for much greater compiler
compatibility and device targeting. Currently we do this off the fparser2 AST but there
shouldn't be anything preventing us from doing the same from the Flang AST.

Steps:
- add LLVM Flang dependency

STATUS
Stage 1, Stage 2 and Stage 3 are implemented and complete for --parser flang
(see translator-v2/flang-scan/README.md for details): op2-flang-scan builds a
JSON description of each subprogram - parameters, dependency names, cooked
source text for kernel emission, a simplified expression-tree walk of its
assignments/calls/local-array declarations (Stage 2), and now also a fully
typed declaration list and nested statement tree (Stage 3, see the
"Declaration serialization" / "Statement-tree serialization" sections of
op2-flang-scan.cpp). op2-translator/fortran/flang_validator.py ports every
Stage 2 check (read/const-write/increment/slice/runtime-dimension) to walk
that JSON instead of an fparser2 AST, and
op2-translator/fortran/flang_kernels_c.py + flang_kernels.py port Stage 3
(kernel-to-C++ translation, plus the const-rename/hydra-IO/atomicAdd JSON-tree
transforms fortran/schemes.py applies beforehand) the same way. fparser2 is
only used as a fallback: per-file, if Flang fails to parse a source file;
per-loop, if validation or translation needs a dependency that wasn't parsed
by Flang. Every kernel translation scheme (Fortran/seq, openmp, cuda, c_seq,
c_cuda, c_hip) and Fortran main-program translation (op_par_loop/op_decl_const
call rewriting) are Flang-native when --parser flang is selected and Flang
successfully parsed the relevant sources. That includes every registered
Fortran kernel scheme: seq, openmp, cuda, c_seq, c_cuda, and c_hip.

Verified end-to-end on apps/fortran/airfoil, jac1 and reduction: with
--parser flang, translating with -t c_seq/c_cuda/c_hip produces kernel C++
files byte-identical to the fparser2 path (aside from a content-hash-derived
prelude macro name in the CUDA/HIP master kernel file, which is expected to
differ run-to-run regardless of parser backend). Fortran/cuda (FortranCuda)
is also Flang-native: const rename, hydra IO, EXTERNAL stripping, SoA/gbl
stride insertion, and Fortran-style atomicAdd rewriting all run on
flang_source without an fparser2 AST (verified on airfoil with the
test_no_fparser2_audit harness). Fortran/openmp is likewise Flang-native
(including the SIMD `rename_entities` + `insert_strides` path). Formatting
differs from fparser2's pretty printer (Flang cooked source is
lowercase/compact) but the semantic rewrites match. A full
airfoil_plain_cuda build still needs a CUDA Fortran compiler (e.g.
nvfortran; F_HAS_CUDA); this environment only has gfortran.

Parser equivalence suite: translator-v2/parser_eval/
(airfoil + unstructured tri_diff + mesh_res).
